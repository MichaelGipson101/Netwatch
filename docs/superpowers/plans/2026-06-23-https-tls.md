# HTTPS/TLS for the Dashboard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Serve the netwatch dashboard over real, browser-trusted HTTPS at `https://netwatch.thelanternarchive.com`, reachable only over the existing Tailscale network, without changing `monitor.py` or its existing plain-HTTP LAN path.

**Architecture:** Caddy runs as a second systemd service on `applepi5`, gets a Let's Encrypt certificate via Cloudflare DNS-01 (the `netwatch` subdomain is delegated from Bluehost to Cloudflare specifically so this works), terminates TLS on `:443`, and reverse-proxies to `monitor.py` on `127.0.0.1:8080`. `monitor.py` keeps binding `0.0.0.0:8080` unchanged.

**Tech Stack:** Caddy (custom build with the `caddy-dns/cloudflare` plugin, downloaded prebuilt — no local Go toolchain needed), systemd, Cloudflare DNS API, Let's Encrypt (via Caddy's built-in ACME client).

## Global Constraints

- Spec: `docs/superpowers/specs/2026-06-23-https-tls-design.md`
- No changes to `monitor.py` — it keeps binding `0.0.0.0:8080` exactly as today.
- No port-forwarding, no Tailscale Funnel, no actual internet exposure — the domain resolves to a Tailscale-only IP (`100.82.194.34`).
- The Cloudflare API token must never be committed to the netwatch git repo or pasted into chat — it lives only in a root/caddy-owned file on disk (`/etc/caddy/caddy.env`, mode 600).
- Target machine: `applepi5`, Debian 13 (trixie), `aarch64` (Caddy's "arm64" build), passwordless sudo available for the `mgipson` user.
- No automated test suite applies — this is infrastructure work; verification is operational (curl, systemctl, journalctl).

### Task 1: Manual DNS delegation and Cloudflare API token (user-performed)

**Files:** none — this task happens entirely in the Porkbun and Cloudflare web dashboards, not in this repo or on this machine.

**Interfaces:**
- Produces: a working `netwatch.thelanternarchive.com` → `100.82.194.34` DNS record resolvable from the public internet, and a Cloudflare API token scoped to that zone's DNS — both required before Task 5 (writing the Caddyfile) can actually issue a certificate.

This task cannot be automated or delegated to a subagent — it requires logging into two web dashboards you control. Steps:

- [ ] **Step 1: Add the domain to Cloudflare**

In a browser, go to https://dash.cloudflare.com, sign up for a free account if you don't have one, click "Add a Site", enter `thelanternarchive.com`. When asked about plan, pick Free. When Cloudflare scans existing DNS records, you don't need to import anything from Bluehost — this Cloudflare zone will only ever hold the one `netwatch` record; the rest of your site's DNS stays on Bluehost.

- [ ] **Step 2: Add the A record in Cloudflare**

In the Cloudflare dashboard, under DNS → Records for `thelanternarchive.com`, add:
- Type: `A`
- Name: `netwatch`
- IPv4 address: `100.82.194.34`
- Proxy status: **DNS only** (the gray cloud, not the orange "proxied" cloud — Cloudflare's CDN/proxy must be off here, since this IP is only reachable over Tailscale and Cloudflare's proxy servers aren't on your tailnet)
- TTL: Auto

- [ ] **Step 3: Note Cloudflare's assigned nameservers**

Cloudflare will show you two nameservers (something like `xxx.ns.cloudflare.com` and `yyy.ns.cloudflare.com`) for the zone. Write these down — you'll need them in Step 4.

- [ ] **Step 4: Delegate just the `netwatch` subdomain at Porkbun**

Log into Porkbun (https://porkbun.com/account/domainsSpeedy), find `thelanternarchive.com`, open its DNS records editor. You need to add an `NS` record scoped to the `netwatch` subdomain only (not the root domain — the root stays pointed at Bluehost):
- Type: `NS`
- Host: `netwatch`
- Answer: the first Cloudflare nameserver from Step 3
- Add a second `NS` record, same Host (`netwatch`), Answer: the second Cloudflare nameserver

Porkbun's editor may label this "Subdomain NS delegation" or just let you add multiple NS records with the same host value — if you don't see a way to scope an NS record to a single subdomain (rather than the whole zone), stop and tell me what the editor actually shows, since some registrars only support NS delegation at the root.

- [ ] **Step 5: Verify delegation propagated**

DNS propagation can take a few minutes to a few hours. Check from this machine:

```bash
dig NS netwatch.thelanternarchive.com +short
```

Expected: the two Cloudflare nameservers from Step 3. If you see Bluehost's nameservers instead, the delegation hasn't propagated yet — wait and retry.

Once that resolves correctly, also check:

```bash
dig A netwatch.thelanternarchive.com +short
```

Expected: `100.82.194.34`.

- [ ] **Step 6: Generate a scoped Cloudflare API token**

In Cloudflare, go to My Profile → API Tokens → Create Token → "Create Custom Token". Set:
- Permissions: `Zone` / `DNS` / `Edit`
- Zone Resources: `Include` / `Specific zone` / `thelanternarchive.com`

Create it and copy the token value. **Do not paste this token into our chat.** You'll enter it directly into a file on this machine in Task 5.

- [ ] **Step 7: Confirm with me**

Once Steps 1-6 are done and Step 5's `dig` checks return the expected values, tell me to continue — I'll proceed with the on-machine installation tasks. Keep the API token from Step 6 somewhere you can paste it from when we reach Task 5.

### Task 4: Download and install the Caddy binary with the Cloudflare DNS plugin

**Files:**
- Create: `/usr/local/bin/caddy` (binary, not part of this git repo)

**Interfaces:**
- Produces: an executable `/usr/local/bin/caddy` with the `caddy-dns/cloudflare` module built in, required by Task 7 (`ExecStart=/usr/local/bin/caddy run ...`).

- [ ] **Step 1: Download the custom build**

Caddy's official build server compiles a binary with whichever plugins you request, no local Go toolchain needed. This machine is `aarch64` (Caddy calls this `arm64`):

```bash
curl -sL "https://caddyserver.com/api/download?os=linux&arch=arm64&p=github.com/caddy-dns/cloudflare" -o /tmp/caddy
```

- [ ] **Step 2: Verify the download**

```bash
file /tmp/caddy
```

Expected: something like `/tmp/caddy: ELF 64-bit LSB executable, ARM aarch64, ...` — confirms it's a real binary for this architecture, not an error page saved to a file.

- [ ] **Step 3: Install it**

```bash
sudo install -o root -g root -m 755 /tmp/caddy /usr/local/bin/caddy
rm /tmp/caddy
```

- [ ] **Step 4: Verify the plugin is built in**

```bash
/usr/local/bin/caddy list-modules | grep cloudflare
```

Expected: a line containing `dns.providers.cloudflare`. If this prints nothing, the download didn't include the plugin — re-check Step 1's URL.

### Task 5: Write the Caddyfile and the Cloudflare token env file

**Files:**
- Create: `/etc/caddy/Caddyfile`
- Create: `/etc/caddy/caddy.env`

**Interfaces:**
- Consumes: the Cloudflare API token from Task 1, Step 6 (the human has it, not pasted into chat).
- Produces: `/etc/caddy/Caddyfile` and `/etc/caddy/caddy.env`, both read by Task 7's systemd unit (`ExecStart` reads the Caddyfile; `EnvironmentFile=` reads the env file for `CF_API_TOKEN`).

- [ ] **Step 1: Write the Caddyfile**

```bash
sudo tee /etc/caddy/Caddyfile > /dev/null <<'EOF'
netwatch.thelanternarchive.com {
    tls {
        dns cloudflare {env.CF_API_TOKEN}
    }
    reverse_proxy 127.0.0.1:8080
}
EOF
sudo chown root:caddy /etc/caddy/Caddyfile
sudo chmod 640 /etc/caddy/Caddyfile
```

- [ ] **Step 2: Create the env file with a placeholder, then edit it yourself**

I will create the file with a placeholder (so I never see or transmit the real value):

```bash
sudo tee /etc/caddy/caddy.env > /dev/null <<'EOF'
CF_API_TOKEN=REPLACE_ME
EOF
sudo chown root:caddy /etc/caddy/caddy.env
sudo chmod 640 /etc/caddy/caddy.env
```

Now **you** (not me) replace the placeholder with the real token from Task 1, Step 6, directly in your own terminal:

```bash
sudo nano /etc/caddy/caddy.env
```

Replace `REPLACE_ME` with the actual token value, save, exit.

- [ ] **Step 3: Verify the file exists with correct permissions (without reading its contents)**

```bash
sudo stat -c '%U:%G %a' /etc/caddy/caddy.env
```

Expected: `root:caddy 640`. Confirm with me that you've completed Step 2 before moving to Task 6 — I won't read the file's contents to check.

- [ ] **Step 4: No commit needed**

These files live outside the git repo entirely (`/etc/caddy/`), so there is nothing to commit — and the token must never end up in git history regardless.

### Task 6: Allow Caddy to bind port 443 without running as root

**Files:** none (capability grant only — actually handled in Task 7's systemd unit via `AmbientCapabilities`)

**Interfaces:**
- Produces: confirmation that the systemd capability mechanism used in Task 7 (`AmbientCapabilities=CAP_NET_BIND_SERVICE`) is sufficient on this kernel, so Task 7 doesn't silently fail to bind `:443`.

Ports below 1024 normally require root. Rather than running Caddy as root, the systemd unit in Task 7 grants just the one capability needed. There's nothing to do in this task except confirm the kernel supports it (it does on any modern Linux, including Debian 13) — this task exists only to flag the mechanism before Task 7 relies on it silently. No commands to run; proceed to Task 7.

- [ ] **Step 1: Acknowledge and proceed**

No action — continue to Task 7. (If Task 7's verification later shows Caddy failing to bind `:443` with a permissions error, revisit this task: the fallback is `sudo setcap 'cap_net_bind_service=+ep' /usr/local/bin/caddy`, but try the systemd-unit approach first since it doesn't require re-applying the capability every time the binary is replaced.)

### Task 7: Create and start the `caddy` systemd service

**Files:**
- Create: `/etc/systemd/system/caddy.service`

**Interfaces:**
- Consumes: `/usr/local/bin/caddy` (Task 4), `/etc/caddy/Caddyfile` and `/etc/caddy/caddy.env` (Task 5), the `caddy` user (Task 2).
- Produces: a running `caddy` service that Task 8's verification checks against.

- [ ] **Step 1: Write the unit file**

```bash
sudo tee /etc/systemd/system/caddy.service > /dev/null <<'EOF'
[Unit]
Description=Caddy reverse proxy for Netwatch (TLS via Tailscale)
After=network-online.target netwatch.service
Wants=network-online.target

[Service]
Type=simple
User=caddy
Group=caddy
ExecStart=/usr/local/bin/caddy run --config /etc/caddy/Caddyfile --adapter caddyfile
ExecReload=/usr/local/bin/caddy reload --config /etc/caddy/Caddyfile --adapter caddyfile
EnvironmentFile=/etc/caddy/caddy.env
AmbientCapabilities=CAP_NET_BIND_SERVICE
NoNewPrivileges=true
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal
SyslogIdentifier=caddy

[Install]
WantedBy=multi-user.target
EOF
```

- [ ] **Step 2: Reload systemd and start the service**

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now caddy
```

- [ ] **Step 3: Check it started cleanly**

```bash
sudo systemctl status caddy --no-pager
```

Expected: `Active: active (running)`.

- [ ] **Step 4: Check the ACME issuance log**

```bash
sudo journalctl -u caddy --no-pager | grep -i -E "certificate obtained|obtaining certificate|error"
```

Expected: a line indicating a certificate was successfully obtained for `netwatch.thelanternarchive.com`. If you see repeated errors mentioning Cloudflare authentication, the token in `/etc/caddy/caddy.env` (Task 5) is likely wrong — re-check it (you'll need to edit the file yourself again, same as Task 5 Step 2, then `sudo systemctl restart caddy`).

- [ ] **Step 5: No commit needed**
